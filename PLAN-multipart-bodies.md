# Multipart Body Support Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a flow see inside a `multipart/form-data` webhook — address a named file's filename, content type, size, and bytes, and its sibling form fields — so an operator can filter, route, script, and publish an upload instead of treating the whole request as one opaque blob.

**Architecture:** One new `envelope` body format. `body_format: multipart` parses the verified bytes with stdlib `mime/multipart` into a plain `map[string]any` of the shape `{fields: {...}, files: {...}}`, where each file carries `filename`, `content_type`, `size`, and base64 `content`. Because the result is ordinary nested maps, `filter`, `code`, `publish`, and `graph`'s branch cloning all work with **zero changes** — that is the whole reason for this shape. Parsing is bounded by a new nested `multipart:` option block (max parts, max bytes per part, and whether to carry content at all) so a hostile upload cannot amplify memory. No new node type, no new payload type, no changes to `internal/graph`.

**Tech Stack:** Go (stdlib `mime`, `mime/multipart`, `encoding/base64` — verified WASM-safe), `invopop/jsonschema` for schema generation, vitest for the builder copy, `make` targets for verification.

**Spec:** None written — this plan was designed directly in conversation from a survey of the existing body path. The "Context & Design Decisions" section below carries the full design rationale and is the spec; read it before Task 1.

**Depends on:** Nothing, but see the note in decision 8: if `PLAN-xml-body-support.md` has already landed, Task 4 of this plan must extend that plan's `bodyFormatIssues` walk rather than write a second one. Check for `bodyFormatIssues` in `internal/flowconfig/lint.go` before starting Task 4.

## Global Constraints

- **`internal/flowconfig` and everything it imports must stay WASM-safe.** It compiles to `GOOS=js GOARCH=wasm` via `cmd/hookway-wasm` (`Makefile` target `wasm`) for the builder's live validation. `mime` and `mime/multipart` were verified to build under `GOOS=js GOARCH=wasm` before this plan was written, so the dependency is safe — but Task 1 Step 6 re-proves it rather than trusting this line.
- **Node option structs are the schema source of truth.** `web/src/graph/nodeSchema.json` is generated by `make node-schema` from `hookway schema --nodes`. Never hand-edit it. `make node-schema-check` fails CI on drift.
- **I6 holds: auth verifies raw bytes, never a re-serialized body.** Parsing happens in the `envelope` node, which is `PortVerified` → `PortEnvelope` and therefore already post-auth by construction. **No task may parse a multipart body before auth.** An unsigned upload must never reach the multipart reader.
- **Every limit is enforced before allocation, not after.** A multipart body is an attacker-controlled part count and per-part size behind one Content-Length. Counting parts after reading them, or reading a part fully before checking its size, defeats the limit. Task 1's tests include the adversarial cases.
- **A vendor-supplied filename is data, never a path.** Nothing in this plan may pass a filename to a filesystem call, use it as a map key that later becomes a path, or interpolate it into a URL. It is stored as a string field and nothing else. `filepath.Base` is not a sanitizer and must not appear as though it were one.
- **Bodies stay in memory; this plan does not change that.** `read_body` already buffers the whole request (`internal/flowconfig/node_body.go:44-45`). Multipart parsing adds a second copy of any part whose content is carried. See decision 6 for the memory arithmetic an operator has to do, and the follow-ups for the streaming answer.
- **Commit convention:** one commit per task, conventional-commit prefixes, and this repo does **not** push by default — leave commits local unless the operator asks otherwise. If your harness supplies a `Co-Authored-By` attribution trailer, append it.
- **Verification commands** (run from repo root): `make test`, `make lint`, `make deadcode`, `make wasm`, `make validate-examples`, `make node-schema-check`, `cd web && npm run test`.

## Context & Design Decisions

Read this before writing code. It is the spec.

**What exists today.** Nothing parses multipart. A repo-wide search for `multipart`, `FormFile`, and `ParseMultipart` returns no hits outside this plan. A `multipart/form-data` webhook therefore takes the generic non-JSON path: `BuildEnvelopeWithOptions` tries `json.Unmarshal`, fails, and base64-encodes the **entire raw body** — boundaries, part headers, every part concatenated — into `raw_body_base64` (`internal/webhook/envelope.go:112-118`). `envelope.Body` is nil.

What that means in practice:
- `filter` cannot address anything. The body is nil, so `walkBodyPath` reports every path missing — the same silent never-match described in `PLAN-xml-body-support.md`.
- `code` receives `null` as `input.body`.
- A consumer downstream gets one base64 string it must itself MIME-parse to recover the file.
- `http_request` with `body: raw` **does** forward the original bytes intact, so straight proxying of an upload already works today and this plan does not change it.

So the gap is precisely *inspection*: a flow cannot branch on which file arrived, what it is called, what type it claims, or how big it is.

**Eight decisions, and why:**

1. **This is a `body_format`, not a new node.** `envelope.body_format` is already the "how do I decode the verified bytes" knob, with `json`, `xml`, and `raw` (`internal/flowconfig/nodes.go:68-70`). Multipart is a fourth answer to that same question. A separate `multipart` node would need its own place in the port graph, would let an operator put it before the envelope where the body is not yet decoded, and would make "what shape is the body here" depend on two nodes instead of one. The lint guard in Task 4 exists precisely because that question needs one answer per path.

2. **The parsed shape is plain `map[string]any`, and that is the load-bearing decision.** `graph`'s branch cloning already deep-copies `map[string]any` and `[]any` recursively (`internal/graph/clone.go:86-105`), `filter`'s `walkBodyPath` already walks nested maps by dotted key (`internal/filter/filter.go:325-341`), `code`'s `cloneJSONValue` already round-trips through JSON (`node_code.go:123-136`), and `publish` already marshals `env.Body` as the envelope's `body`. Choosing a custom struct — the way XML chose `transform.Document` — would mean touching every one of those, exactly as `PLAN-xml-body-support.md` has to. Choosing maps means Tasks 2 and 3 of that plan have no analogue here. Pay the small cost (a base64 string instead of `[]byte`) to avoid four integrations.

3. **Files are keyed by form field name, not a list, so filter paths can reach them.** `walkBodyPath` does not support array indexing, and is not going to in this plan. A `files: [...]` list would be completely unaddressable by a filter — the feature would ship inspectable by `code` only. So files is a map: `files.document.content_type` resolves with the existing dotted-path code and no filter changes at all. When a field name repeats (a `files[]`-style upload), the second and later parts get `name#2`, `name#3`, keyed in document order — `#` is not the path separator, so `files.document#2.filename` stays addressable. This is documented, not clever; see the limits table in Task 6.

4. **`content` is base64 and opt-outable.** Base64 inflates a part by 4/3, and an operator who only routes on filename and type should not pay that. `include_content` defaults to **true**, because a template that gives you metadata and drops the file is surprising, and the metadata-only mode is the optimization rather than the default. An operator who wants metadata only sets `include_content: false`, and each file then carries `size` and a `content_omitted: true` marker — a marker rather than a missing key, so a `code` script can tell "no content carried" apart from "empty file".

5. **Three bounds, all enforced while streaming, with a dedicated status per failure.** A part count cap (`max_parts`, default 16), a per-part byte cap (`max_part_bytes`, default 1 MiB), and nothing else — the total is already bounded by `read_body.max_bytes` upstream. `max_parts` is checked as parts are pulled, before the next one is read. `max_part_bytes` is enforced with `io.LimitReader(part, max+1)` and a length check, the same trick `read_body` uses (`node_body.go:44-56`) and the same one `http_request` uses for upstream bodies (`node_http_request.go:135-145`). Exceeding either is a `413`, not a `400`, so an operator reading logs can tell "too big" from "malformed".

6. **Memory is the honest cost, and the docs must say so.** With content carried, peak footprint per in-flight request is roughly `raw body` (from `read_body`) + `sum of carried part sizes` + `4/3 × that` (the base64 strings) + a transient copy per branch that clones the body. A 10 MiB upload on a flow with two publish branches is not 10 MiB. The bound an operator actually controls is `max_parts × max_part_bytes`, and the defaults (16 × 1 MiB) are chosen so the worst case stays modest rather than so the feature feels generous. Task 6 documents the arithmetic and points at the streaming follow-up.

7. **No multipart *re-serialization*.** `http_request` with `body: transformed` will JSON-marshal the parsed shape, which is almost certainly not what someone forwarding an upload wants. Rebuilding a multipart body from the parsed map (boundary generation, part header reconstruction, ordering) is a real chunk of work whose only consumer is "forward the upload after editing it" — and forwarding it *unedited* already works with `body: raw`. So: v1 does not re-serialize, Task 6 documents `body: raw` as the forwarding answer, and the follow-ups list re-serialization. This is the plan's main deliberate omission and it should stay omitted unless someone asks for it.

8. **A validate-time guard, shared with the XML plan if that has landed.** `body_format: multipart` plus `transform kind: field_map`/`changed_fields` is a runtime failure (those walk JSON object paths and the parsed shape is not the event's JSON body), and `kind: xml_prune` on a multipart body is likewise a runtime 400. These are decidable from config. `PLAN-xml-body-support.md` Task 3 builds exactly this graph walk (`bodyFormatIssues`); if it is already in `internal/flowconfig/lint.go`, Task 4 here **extends** it with the multipart cases rather than adding a second traversal. If it is not there, Task 4 writes a scoped-down version covering only multipart. Check first.

**What this deliberately does not do.**
- **No streaming to disk or blob storage.** The body stays in memory. An intake that streams a large upload to S3 and publishes a pointer is a different feature with a different shape (it needs a destination, a URL contract, and a cleanup story) and is the right answer for genuinely large files.
- **No multipart re-serialization**, per decision 7.
- **No `multipart/mixed` or `multipart/related`.** Only `multipart/form-data`, which is what webhook vendors send. The parser reads the boundary from the Content-Type and rejects a media type that is not `multipart/form-data`.
- **No content-type sniffing.** A part's `content_type` is what the vendor claimed in its part headers, verbatim. Inferring the real type from magic bytes invites a mismatch between what a filter matched and what a consumer receives; if an operator wants to verify, a `code` node can read the base64.
- **No size guard on the published envelope.** A multipart publish to SQS/SNS can exceed the provider's 256 KB message cap, and nothing in this repo checks that today for any body type. Fixing it belongs in a queue plan, not here.

```go
package flowconfig

import (
	"bytes"
	"encoding/base64"
	"fmt"
	"mime/multipart"
	"net/http"
	"strings"
	"testing"
)

// buildMultipart writes a multipart/form-data body and returns it with the
// matching Content-Type, so tests exercise a real boundary rather than a
// hand-written string that could drift from what the stdlib writer produces.
func buildMultipart(t *testing.T, fields map[string]string, files []multipartFile) (string, []byte) {
	t.Helper()
	var buf bytes.Buffer
	w := multipart.NewWriter(&buf)
	for name, value := range fields {
		if err := w.WriteField(name, value); err != nil {
			t.Fatal(err)
		}
	}
	for _, f := range files {
		h := make(map[string][]string)
		h["Content-Disposition"] = []string{fmt.Sprintf(`form-data; name=%q; filename=%q`, f.field, f.filename)}
		if f.contentType != "" {
			h["Content-Type"] = []string{f.contentType}
		}
		part, err := w.CreatePart(h)
		if err != nil {
			t.Fatal(err)
		}
		if _, err := part.Write(f.content); err != nil {
			t.Fatal(err)
		}
	}
	if err := w.Close(); err != nil {
		t.Fatal(err)
	}
	return w.FormDataContentType(), buf.Bytes()
}

type multipartFile struct {
	field, filename, contentType string
	content                     []byte
}

func defaultLimits() multipartLimits {
	return multipartLimits{MaxParts: 16, MaxPartBytes: 1 << 20, IncludeContent: true}
}

func TestParseMultipartExtractsFieldsAndFiles(t *testing.T) {
	ct, body := buildMultipart(t,
		map[string]string{"event": "upload", "account": "acct_1"},
		[]multipartFile{{field: "document", filename: "report.pdf", contentType: "application/pdf", content: []byte("PDF-BYTES")}},
	)
	out, status, err := parseMultipart(ct, body, defaultLimits())
	if err != nil {
		t.Fatalf("parseMultipart = %v (status %d)", err, status)
	}
	fields, ok := out["fields"].(map[string]any)
	if !ok {
		t.Fatalf("fields = %T, want map[string]any", out["fields"])
	}
	if fields["event"] != "upload" || fields["account"] != "acct_1" {
		t.Fatalf("fields = %#v, want event=upload account=acct_1", fields)
	}
	files, ok := out["files"].(map[string]any)
	if !ok {
		t.Fatalf("files = %T, want map[string]any", out["files"])
	}
	doc, ok := files["document"].(map[string]any)
	if !ok {
		t.Fatalf("files.document = %T, want map[string]any", files["document"])
	}
	if doc["filename"] != "report.pdf" {
		t.Fatalf("filename = %v, want report.pdf", doc["filename"])
	}
	if doc["content_type"] != "application/pdf" {
		t.Fatalf("content_type = %v, want application/pdf", doc["content_type"])
	}
	if doc["size"] != int64(len("PDF-BYTES")) {
		t.Fatalf("size = %v (%T), want %d", doc["size"], doc["size"], len("PDF-BYTES"))
	}
	decoded, decErr := base64.StdEncoding.DecodeString(doc["content"].(string))
	if decErr != nil {
		t.Fatalf("content is not base64: %v", decErr)
	}
	if string(decoded) != "PDF-BYTES" {
		t.Fatalf("decoded content = %q, want PDF-BYTES", decoded)
	}
}

// The shape must be addressable by the existing dotted-path filter code, which
// cannot index a list. This test is the contract with internal/filter.
func TestParseMultipartShapeIsDottedPathAddressable(t *testing.T) {
	ct, body := buildMultipart(t, nil,
		[]multipartFile{{field: "document", filename: "a.pdf", contentType: "application/pdf", content: []byte("x")}},
	)
	out, _, err := parseMultipart(ct, body, defaultLimits())
	if err != nil {
		t.Fatal(err)
	}
	// Mirror what filter.walkBodyPath does: successive map[string]any lookups.
	var current any = out
	for _, segment := range []string{"files", "document", "content_type"} {
		m, ok := current.(map[string]any)
		if !ok {
			t.Fatalf("segment %q: value is %T, not a map — a filter could not walk this", segment, current)
		}
		current, ok = m[segment]
		if !ok {
			t.Fatalf("segment %q missing", segment)
		}
	}
	if current != "application/pdf" {
		t.Fatalf("walked to %v, want application/pdf", current)
	}
}

func TestParseMultipartRepeatedFieldNamesAreSuffixed(t *testing.T) {
	ct, body := buildMultipart(t, nil, []multipartFile{
		{field: "attachment", filename: "one.txt", contentType: "text/plain", content: []byte("1")},
		{field: "attachment", filename: "two.txt", contentType: "text/plain", content: []byte("2")},
		{field: "attachment", filename: "three.txt", contentType: "text/plain", content: []byte("3")},

		t.Fatal(err)

		}
	}

func TestParseMultipartRejectsTooManyParts(t *testing.T) {
	var files []multipartFile
	for i := 0; i < 5; i++ {
		files = append(files, multipartFile{field: fmt.Sprintf("f%d", i), filename: "x.txt", content: []byte("x")})
	}
	ct, body := buildMultipart(t, nil, files)
	lim := defaultLimits()
	lim.MaxParts = 3
	_, status, err := parseMultipart(ct, body, lim)
	if err == nil {
		t.Fatal("parseMultipart = nil error, want a rejection for exceeding max_parts")

	if status != http.StatusRequestEntityTooLarge {
		t.Fatalf("status = %d, want 413 so an operator can tell too-big from malformed", status)

		t.Fatalf("error = %v, want it to name max_parts", err)
	}

// The per-part cap must stop the read rather than buffer the whole part and

		t.Fatalf("status = %d, want 413", status)
	}
}
```

```go
package flowconfig

import (
	"bytes"
	"encoding/base64"
	"errors"
	"fmt"
	"io"
	"mime"
	"mime/multipart"
	"net/http"
	"strings"
)

// multipartLimits bounds a parse. A multipart body is an attacker-controlled
// part count and per-part size hiding behind one Content-Length, so both are
// enforced while streaming rather than measured after buffering.
type multipartLimits struct {
	MaxParts       int
	MaxPartBytes   int64
	IncludeContent bool
}

// parseMultipart decodes a multipart/form-data body into the shape the rest of
// the flow works with:
//
//	{
//	  "fields": {"event": "upload"},
//	  "files":  {"document": {filename, content_type, size, content}}
//	}
//
// Every value is a string, int64, bool, or map[string]any, which is what makes
// this shape free to integrate: graph's branch cloning already deep-copies
// nested maps, filter's walkBodyPath already walks them by dotted key, and the
// code node's cloneJSONValue already round-trips them through JSON.
//
// Files are keyed by form field name rather than collected into a list because
// walkBodyPath cannot index a list — a list would make the feature
// inspectable by scripts only. A repeated field name gets a "#2", "#3" suffix
// in document order; "#" is not the path separator, so files."document#2"
// stays addressable.
//
// It returns the parsed shape, the HTTP status to report when err is non-nil
// (400 for malformed input, 413 for a limit), and the error. On success the
// status is 0.
func parseMultipart(contentType string, body []byte, lim multipartLimits) (map[string]any, int, error) {
	mediaType, params, err := mime.ParseMediaType(contentType)
	if err != nil {
		return nil, http.StatusBadRequest, fmt.Errorf("content-type %q is not parseable: %w", contentType, err)
	}
	// Only form-data. multipart/mixed and multipart/related are not what
	// webhook vendors send and are deliberately out of scope.
	if !strings.EqualFold(mediaType, "multipart/form-data") {
		return nil, http.StatusBadRequest, fmt.Errorf("body_format: multipart needs content-type multipart/form-data, got %q", mediaType)
	}
	boundary := params["boundary"]
	if boundary == "" {
		return nil, http.StatusBadRequest, errors.New("multipart/form-data content-type has no boundary parameter")
	}

	fields := map[string]any{}
	files := map[string]any{}
	reader := multipart.NewReader(bytes.NewReader(body), boundary)
	seen := map[string]int{}
	count := 0
	for {
		part, err := reader.NextPart()
		if err == io.EOF {
			break
		}
		if err != nil {
			return nil, http.StatusBadRequest, fmt.Errorf("multipart body is malformed: %w", err)
		}
		// Counted before the part is read, so a body with a thousand parts is
		// rejected after reading three rather than after reading all thousand.
		count++
		if count > lim.MaxParts {
			part.Close()
			return nil, http.StatusRequestEntityTooLarge, fmt.Errorf("multipart body has more than max_parts (%d) parts", lim.MaxParts)
		}
		name := part.FormName()
		filename := part.FileName()

		// LimitReader with max+1 is how read_body and http_request both detect
		// an overrun: read one byte past the cap and compare, so the parser
		// never holds more than cap+1 bytes of a part.
		limited := io.LimitReader(part, lim.MaxPartBytes+1)
		content, readErr := io.ReadAll(limited)
		part.Close()
		if readErr != nil {
			return nil, http.StatusBadRequest, fmt.Errorf("multipart part %q: %w", name, readErr)
		}
		if int64(len(content)) > lim.MaxPartBytes {
			return nil, http.StatusRequestEntityTooLarge, fmt.Errorf("multipart part %q exceeds max_part_bytes (%d)", name, lim.MaxPartBytes)
		}

		if filename == "" {
			// A part with no filename is a form field. A repeated field name
			// keeps the last value, matching net/http's own form semantics.
			fields[name] = string(content)
			continue
		}
		key := name
		if n := seen[name]; n > 0 {
			key = fmt.Sprintf("%s#%d", name, n+1)
		}
		seen[name]++

		file := map[string]any{
			// filename is the vendor's claim, stored as data. Nothing in
			// Hookway passes it to a filesystem call or a URL.
			"filename": filename,
			// content_type is likewise what the vendor claimed in the part
			// headers, verbatim: no magic-byte sniffing, because a sniffed
			// value could disagree with what a filter matched on.
			"content_type": part.Header.Get("Content-Type"),
			"size":         int64(len(content)),
		}
		if lim.IncludeContent {
			file["content"] = base64.StdEncoding.EncodeToString(content)
		} else {
			// A marker rather than a missing key, so a script can tell "no
			// content carried" from "the file was empty".
			file["content_omitted"] = true
		}
		files[key] = file
	}
	return map[string]any{"fields": fields, "files": files}, 0, nil
}
```

```go
// bodyFormatIssues rejects a transform whose kind cannot read the body the
// flow's envelope produced. Both combinations below are a runtime 400 in
// node_transform.go today and are fully decidable from the config.
//
// It walks forward from the trigger carrying the format established by the
// last envelope on each path, because a flow may have several envelope nodes
// on different branches of a switch — "does this flow contain a multipart
// envelope" is the wrong question. This mirrors lookupBeforeFilterIssues.
func bodyFormatIssues(prefix string, fc graph.FlowConfig) []config.ValidationIssue {
	type nodeInfo struct {
		typ   string
		index int
		cfg   graph.NodeConfig
	}
	info := make(map[string]nodeInfo, len(fc.Nodes))
	root := ""
	for i, node := range fc.Nodes {
		info[node.ID] = nodeInfo{typ: node.Type, index: i, cfg: node}
		if node.Type == "http_trigger" && root == "" {
			root = node.ID
		}
	}
	if root == "" {
		return nil
	}
	edges, _ := graph.ParseEdges(fc.Edges)
	out := map[string][]string{}
	for _, edge := range edges {
		out[edge.From] = append(out[edge.From], edge.To)
	}
	type frame struct {
		id     string
		format string
	}
	var issues []config.ValidationIssue
	seen := map[string]bool{}
	reported := map[string]bool{}
	stack := []frame{{id: root}}
	for len(stack) > 0 {
		cur := stack[len(stack)-1]
		stack = stack[:len(stack)-1]
		key := cur.id + ":" + cur.format
		if seen[key] {
			continue
		}
		seen[key] = true
		node, known := info[cur.id]
		if !known {
			continue
		}
		format := cur.format
		switch node.typ {
		case "envelope":
			format = "json"
			if opts, err := decodeOptions[EnvelopeOptions](node.cfg); err == nil && opts.BodyFormat != "" {
				format = opts.BodyFormat
			}
		case "transform":
			if !reported[cur.id] {
				if issue, bad := transformBodyFormatIssue(prefix, node.index, cur.id, format, node.cfg); bad {
					reported[cur.id] = true
					issues = append(issues, issue)
				}
			}
		}
		for _, next := range out[cur.id] {
			stack = append(stack, frame{id: next, format: format})
		}
	}
	return issues
}

// transformBodyFormatIssue rejects a transform kind that cannot read the body
// on its path.
func transformBodyFormatIssue(prefix string, index int, id, format string, nc graph.NodeConfig) (config.ValidationIssue, bool) {
	opts, err := decodeOptions[TransformOptions](nc)
	if err != nil {
		return config.ValidationIssue{}, false
	}
	field := fmt.Sprintf("%s.nodes[%d].kind", prefix, index)
	switch opts.Kind {
	case "xml_prune":
		if format == "multipart" {
			return cfgIssue(field,
				fmt.Sprintf("transform %q uses kind: xml_prune but reaches an envelope with body_format: multipart; the body is not an XML document and the node would fail at runtime", id),
				"use body_format: xml for XML documents",
			), true
		}
	case "field_map", "changed_fields":
		if format == "multipart" {
			return cfgIssue(field,
				fmt.Sprintf("transform %q uses kind: %s but reaches an envelope with body_format: multipart; the parsed body is {fields, files}, not the event's JSON body, and the node would fail at runtime", id, opts.Kind),
				"read the parts in a code node instead",
			), true
		}
	}
	return config.ValidationIssue{}, false
}
```

````markdown
### Multipart bodies

`body_format: multipart` parses a `multipart/form-data` request into a shape
the rest of the flow can address:

```yaml
- id: env
  type: envelope
  body_format: multipart
  multipart:
    max_parts: 4            # parts allowed before the request is rejected (default 16, max 256)
    max_part_bytes: 2097152 # per-part cap (default 1 MiB)
    include_content: true   # carry the bytes as base64 (default true)
```

The body becomes:

```json
{
  "fields": {"account": "acct_1"},
  "files": {
    "document": {
      "filename": "report.pdf",
      "content_type": "application/pdf",
      "size": 20481,
      "content": "<base64>"
    }
  }
}
```

Files are keyed by form field name rather than collected into a list, so the
ordinary dotted-path filter reaches them: `files.document.content_type`. A
repeated field name gets a `#2`, `#3` suffix in document order
(`files.document#2.filename`). `code` sees the same object as `input.body`, and
`publish` sends it as the envelope's `body`.

The signature is always verified against the raw bytes before anything is
parsed, so an unsigned upload never reaches the multipart reader.

**Memory.** The whole request is buffered by `read_body`, and each carried part
is held again, plus a base64 copy at 4/3 its size. Peak footprint per in-flight
request is roughly the raw body plus `4/3 x` the carried content, and again per
branch that clones the body. The bound you control is
`max_parts x max_part_bytes` — the defaults are modest for that reason. Set
`include_content: false` when you only route on metadata: each file then
carries `size` and `content_omitted: true` instead of `content`, and the bytes
are never copied. Genuinely large uploads want a streaming intake, which
Hookway does not have.

**Limits worth knowing before you design around it:**

| Limit | Detail |
| --- | --- |
| Form-data only | `multipart/mixed` and `multipart/related` are rejected with `400`. |
| No re-serialization | `http_request` `body: transformed` JSON-encodes the parsed shape, which is not a multipart body. To forward an upload unchanged, use `body: raw`, which sends the original bytes. |
| Claimed types | `content_type` is what the vendor's part headers said, verbatim. There is no magic-byte sniffing, so a filter matches the claim, not the content. |
| Repeated fields | Non-file fields keep the last value; files get `#2`/`#3` keys. |
| Transform kinds | `field_map`, `changed_fields`, and `xml_prune` all reject a multipart body at validate time — read the parts in a `code` node instead. |
| Statuses | Over `max_parts` or `max_part_bytes` is `413`; a malformed body or a non-form-data content type is `400`. |

`examples/multipart.yaml` is a complete flow.
````

## Follow-ups (not in this plan)

- **Streaming intake and blob offload.** The body stays fully in memory. An intake that streams a large upload to S3 (or any blob destination) and publishes a pointer is the real answer for files above a few MiB. It needs a destination type, a URL/expiry contract, and a cleanup story for events that fail downstream — a plan of its own, and the natural sequel to this one.
- **Multipart re-serialization.** `http_request` `body: transformed` cannot rebuild a multipart body (decision 7). Forwarding an *edited* upload needs boundary generation and part-header reconstruction. Forwarding an unedited one already works with `body: raw`.
- **A published-envelope size guard.** A multipart publish can exceed SQS/SNS's 256 KB message cap, and nothing in this repo checks message size for any body type today. That belongs in a queue plan.
- **Array indexing in filter paths.** The `#2`/`#3` keying exists only because `walkBodyPath` cannot index a list. Real indexing (or an `any`/`all` quantifier) would let files be a list and would help JSON bodies equally — a filter-language change, not a multipart one.
- **Content-type sniffing.** `content_type` is the vendor's claim. An operator who needs the real type can read the base64 in a `code` node; making the node sniff would create a gap between what a filter matched and what a consumer receives.
